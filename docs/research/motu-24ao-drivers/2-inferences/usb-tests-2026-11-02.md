# Inferences from the 2026-11-02 tests

INFERRED. Each item names the observations it rests on (`../hardware/observations-2026-11-02.md`,
OBS) and how strong it is.

- **UI1. The freezes are tied to the MOTU's Ethernet port being connected.** Every freeze had
  Ethernet in, on both Linux and macOS hosts, with and without drivers. Runs with it out had no
  freeze: 44 min with nothing connected, 49 min USB-only on copernicus, and over 3 h 45 min of heavy
  use on euclid, including 3 power-cycles. Rests on: OBS Freezes. Strength: consistent across about
  15 runs, but the cause on the network side is unknown. Nothing on copernicus marked the moment,
  and the owner chose not to root-cause it ("if 'no ethernet' is the answer for now, thats fine by
  me").
- **UI2. The 8-channel shift is the MOTU losing its frame boundary, triggered by how Linux starts
  playback, not by Linux misplacing data.** Rests on: OBS USB traces (OUT correct, IN slipped by 24
  bytes), OBS mapping (Apple correct on the same device and mode), and the kernel reading in
  `../sources/2026-11-02/rotation-kernel-code.md`: `snd-usb-audio` cuts and copies whole frames and
  cannot itself shift by 24 bytes. Strength: strong for "Linux data is right". The device-side
  mechanism (why 24 bytes, why 1 frame in 6 at first) is not known.
- **UI3. A loopback cannot say whether the slip is on playback or capture.** On the cluster,
  `playback_1` was heard on output 17 (2026-11-01) with no capture involved, which points to a
  playback-side slip of the same size.
- **UI4. `playback_first` is what fixes it, not the order the application opens the streams.**
  Rests on: OBS mapping (49 of 49 with the flag in either order; 0 of 12 clean without it, in either
  order). Mechanism: with the flag the kernel starts the playback endpoint itself, not after capture
  is running. That is a reading of the flag's purpose in `sound/usb`; it was not traced on the wire.
  Strength: strong on euclid. Untested: Intel xHCI with kernel 6.18.48 (fourier), PipeWire (EAR),
  hours of streaming.
- **UI5. The ~2 s of silence at each start is the MOTU's.** It appears with Apple's driver too, and
  the MOTU returns zeros while Linux already sends audio. For EAR it means silence once when a
  `card` node starts or restarts, because the node's streams then stay open.
- **UI6. `snd-usb-motu` cannot be judged on euclid.** Its failure came with AMD xHCI event errors
  every period. The kernel-source reviewer's guess is an event ring overflow from the driver's work
  in URB completion; the error code is not printed. It may behave differently on Intel xHCI or EHCI.
  It is not needed now that the stock driver works.
- **UI7. Configuring and monitoring the MOTU over USB is possible in principle.** MOTU's Mac driver
  carries the device's whole HTTP API over the vendor bulk interface (interface 3; see
  `../1-observations/mac-dext.md` D1.12-D1.17). Linux leaves interface 3 unbound, so a userspace
  program could use it. The request framing is only partly known; nothing was tried.
