The pattern's `motu.*(error|fail)` never matches because the driver logs through the usb device (`usb 5-2:`), not under its own name.

run-step obeys the rule: DEAD means stop, leave the driver loaded, print the evidence. So no run can finish until someone fixes motu-watch's pattern, which I was told not to change. That needs a decision from the owner.

Other problems with the plan:
1. In motu-watch, `journalctl | while` with `exit` inside the loop only ends the subshell. The unit can stay "active" after it trips until the next kernel line arrives. run-step treats the DEAD file as the authority and also checks the unit is active.
2. The brief says snd-usb-motu claims interfaces 1 and 2, but its probe makes the card on interface 0 (`if (ifnum == 0) snd_card_new(..., "motuusb", ...)`). The card id `motuusb` and PCM name "MOTU Pro Audio" (device 0) are confirmed in motu-usb-audio.c. Its hardware is fixed: S24_3LE, 24 ch, 48000 only, 2 to 16 periods, at most 2048 frames per period.
3. With snd-usb-motu, starting playback while capture runs calls `usb_set_interface` on both interfaces (lines 601-602). The owner saw firmware freezes around stream starts, so this is the riskiest moment. run-step starts arecord first, as the brief asks. Starting playback first does not avoid it either.
4. The `D24Ao` card id for the stock driver comes from how ALSA names a product called "24Ao"; I could not check it without loading the driver. If the name differs, the run fails at "card not present" with the driver loaded.
5. `quirk_flags` on this kernel is `array of quirkp`, which is consistent with the `VID:PID:flag|!flag` string form. The flag names `validate_rates` and `skip_iface_setup` are taken from the Talos setting, not checked against kernel 7.0's source.
6. The snd-usb-motu README needs the device locked at 48 kHz before the driver binds. The harness cannot check that.
7. Waiting for capture to reach RUNNING before starting aplay is a 10 ms poll of /proc/asound/<card>/pcm0c/sub0/status, because /proc has no event for it. The 5 s limit only fails the step.
8. After a DEAD or a deadline mid-stream, run-step does not kill aplay or arecord, because killing them closes the PCM. It prints their PIDs; a person decides.
9. A recording longer than about 20 min passes arecord's 4 GiB WAV limit, so SECONDS is capped at 1100. analyze runs at about 0.3 × real time on euclid (a 600 s run takes about 3 min).
