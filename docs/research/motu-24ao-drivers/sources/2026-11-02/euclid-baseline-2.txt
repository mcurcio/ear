So the device kept sending capture data.
   - **Playback side (OUT endpoint 0x09):** it shows only 17 submits in the whole stream, at 17:38:34.150-34.919Z and 42.598-43.303Z. It shows nothing for about 7.7 s, 17:38:34.919Z to 17:38:42.598Z (09:38:34-09:38:42 PST), which covers almost all of aplay's playback.
   - The driver sends each playback URB from `capture_complete_urb` and ignores the return value of `usb_submit_urb`. A failed or skipped submission would leave no trace in usbmon.
   - The tones most likely never reached the MOTU, which by itself would explain the all-zero capture. The snaplen hides the payload, so I cannot prove whether the capture data was zeros. A short run with a larger snaplen would show it.
2. **The event-37 cadence matches the driver's period.** The intervals between errors are 42-44 ms (97 times) or 84-86 ms (97 times), which is 1 or 2 ALSA periods of 2048 frames at 48 kHz (42.67 ms). The errors began 32 ms after "PB Copy Sync" and continued after both PCMs had stopped, until stop_streaming_endpoints. Nothing has appeared in the kernel log since 17:38:46.
   - That fits the driver's period-interrupt work: `handle_interval_interrupt` copies a whole period and scans up to 512 microframe buffers inside the URB completion handler, while the controller's interrupt is being handled.
   - TRB type 37 is a Host Controller Event. A plausible cause is "Event Ring Full", where the controller drops completion events, which would also explain the "missing" playback URBs. Linux does not print the event's completion code, so this is a hypothesis, not verified.
   - The "rec urb error" packets do not show in the visible descriptors, and error_count was 0 throughout.

## Telling a playback rotation from a capture rotation

A digital loopback only measures the two combined (capture map ∘ playback map). To separate them, fix one side by something independent of the computer:
- **Playback alone:** play a tone on one channel only and see which "From Computer" meter, or which physical output, lights in the MOTU's web app. The earlier stock-driver finding (playback N heard on output N-8) was this kind of measurement, if it was taken on physical outputs.
- **Capture alone:** route one known source to a single "To Computer K" and record:
  - an input such as optical/ADAT or a cable from a physical output, or
  - the loopback set to a deliberately non-identity route (only From Computer 1 → To Computer 5, everything else off).
  Whichever channel it lands on gives the capture map. The playback map is then the measured combination with the capture map taken out.
- **Both at once:** with an asymmetric routing in the MOTU, the two cases predict different captured channels. A playback rotation moves where the single routed source lands; a capture rotation moves every channel.
