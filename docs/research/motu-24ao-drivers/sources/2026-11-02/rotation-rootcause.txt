**Main finding: snd-usb-audio cannot create a 24-byte or 8-channel offset for this device.**
- Every OUT packet is whole 72-byte frames: pcm.c:1560-1561 for data, endpoint.c U:298-302 for silence. Implicit-feedback sizes are `actual_length / 72`, an integer division (U:1828).
- Every IN packet is cut to whole frames (pcm.c:1346-1348) and copied at its own offset, with both offset adjustments at 0 for MOTU (stream.c:95-96).
- So the host re-aligns at every packet. A stable +8 has to be a framing slip inside the MOTU, which the host can trigger only through timing or start order.
- The channel map is metadata only; the data paths are plain `memcpy` (pcm.c:1373-1380, 1478-1489). The harness opens `hw:`, so alsa-lib does no routing either.

**Ranked mechanisms**
1. **The OUT stream starts late, is paced by IN, and can run dry** (implicit feedback; most likely trigger).
   - Playback submits no URBs at start (U:1599-1606).
   - Each IN completion releases at most one OUT URB (U:1763-1836, U:468-537), so the OUT queue is only about 1 ms deep.
   - An empty IN URB releases no OUT URB at all (U:1798).
   - OUT URBs have no `URB_ISO_ASAP` (U:1264).
   - MOTU AVB users report 8-channel hopping (Drumfix issue 16). The RolandMueller1994 fork blames gaps in the OUT stream and fixes it with 2 ms of queued silence (`time_silent`) and a `start_frame` check (motu.c:518-533).
   - Trace prediction: the first 0x09 packet comes at least 8 microframes after the first non-empty 0x87 packet. On the lossy starts, about 1.8 s of 0x87 completions with every `actual_length == 0` and no 0x09 submissions. Later, OUT `start_frame` jumps other than +8, or status -18.
   - It does not by itself explain why it is exactly one 8-channel step every time.
2. **Capture-first start order** (pcm.c:712-722 and 1757-1761, U:1488-1521).
   - The only control request at `aplay` start is `SET_INTERFACE(1,1)`, sent while 0x87 is already streaming. There is no `SET_CUR`, because the clock is shared (U:1315-1336, U:1420-1444).
   - Trace prediction: exactly one `SET_INTERFACE` with wIndex 1 and wValue 1 between capture start and the first OUT packet.
   - Talos (ear's order) also showed the shift, so start order alone is not enough.
3. **The IN buffer is 648 bytes per packet, but the device may send up to 1872** (9 frames from 1.5 × nominal; U:1142-1178, U:391).
   - Trace prediction: 0x87 packets with `actual_length == 648` and status -75 or babble, and 0x09 URBs with fewer than 8 packets (pcm.c:1556-1558).
   - This loses frames and feeds #1; it cannot shift bytes.
4. **Rate and interface traffic: the only place the quirk flags act.**
   - `validate_rates` walks every rate at probe (format.c:556-592); it is on by default for MOTU (quirks.c:2434).
   - Without `skip_iface_setup`, probe sets the highest rate and the alternate setting (stream.c:1261-1269).
   - At start, `SET_CUR` is sent only if the rate differs (clock.c:621-623).
   - With euclid's flags this explains the 1.8 s loss only if the lossy starts show a `SET_CUR` (0x21/0x01, wValue 0x0100, wIndex 0x0100) or a CLOCK_VALID read answering 0. It cannot explain +8.
5. **Per-packet truncation of IN and the floor in OUT sizing.** A malformed IN packet (length not a multiple of 72) causes a glitch inside that packet, never a lasting offset.
6. **Ruled out:**
   - The fixed offset adjustments and the 4-byte length header (`TX_LENGTH`) are not set for MOTU.
   - Channel maps.
   - A wrong frame size: there is one alternate setting with 3-byte subslots.
   - v7.0's `packsize` order bug (M:1382 runs before M:1408): fixed in Ubuntu and 6.18.48, and unused by this device's endpoints.
   - Vendor interfaces 3-5: Linux never selects them.

**Decisive check, no new device run needed:** in the existing full-packet pcaps, look at bytes 0-2 of each 72-byte frame.
- If OUT 0x09 frames carry source 1 there and IN 0x87 frames carry source 9, the host sent correct frames and the slip is inside the MOTU.
- If OUT already carries source 9, the host is wrong, which contradicts the code above.

**Suggested lever:** `quirk_flags=07fd:0005:!validate_rates|skip_iface_setup|playback_first`, with aplay started before arecord. OUT URBs then go out at start, before IN starts. This would be a new device step under the safety guards.

## Verdict

1. **Linux is right.** In both runs, every frame Linux sends on OUT 0x09 has source k in slot k (bytes 3(k-1) of each 72-byte frame). The rotation is already in the bytes the MOTU returns on IN 0x87, from the first non-zero sample.
2. **The MOTU slips by one 24-byte group (8 channels × 3 bytes), latched when its path starts.** It is not an ongoing framing fault. In run 2, single-microframe gaps in the OUT stream during steady streaming did not move the map.
3. **Which side: probably OUT, not proven.**
   - A loopback only measures the OUT slip plus the IN slip, so euclid's traces cannot split them.
   - The only direct evidence is from Talos: ear's `playback_1` was heard on output 17, i.e. From Computer j = host slot j+8. That is an OUT-side slip of the same size and direction as euclid's.
   - An IN-side slip with clean OUT fits euclid's data just as well. A one-route loopback test (section 4) separates the two.
4. **When: inside the device's playback-path start, at or after `SET_INTERFACE(1,1)`.** Two Linux start conditions are left, and these traces cannot separate them:
   - **T1:** interface 1 is switched to alt 1 while interface 2 is already streaming (capture first).
   - **T2:** the OUT stream starts paced by IN, with only about one 1 ms URB queued.

   The traces refute every other mechanism ranked in `code.md`.

**Two corrections to `traces.md`:**
- **Burst 16 was cut short.** Only the last ~468 frames (about 10 ms) of source 16's burst came back: IN frame 103631, against source 17's onset at IN frame 104099. The device's path opened at an arbitrary moment inside burst 16, not at a burst boundary.

The 65-90 ms end-to-end figures are ALSA buffering, and the 1.8 s "latency" in `rec.summary.txt` comes from the lost bursts.

**usbmon's `start_frame` cannot show OUT gaps on this controller.**
- IN always has 11 URBs queued, yet consecutive completions report start-frame steps of 0 and 16 (1786 and 1774 times in run 1) instead of a steady 8.
- So the values come from the controller's microframe counter at submit time (xhci-ring.c:4343-4365), not from contiguous frame numbers (4336-4339).
- *Inference:* the AMD controller either lacks contiguous frame IDs or schedules these URBs "as soon as possible". The phase steps above are therefore the only gap evidence, and they are inferred.

## 2. Which side, and when

**What a loopback cannot say.**
- Call the OUT slip a: From Computer j = host OUT slot j+a.
- Call the IN slip b: host capture slot i = To Computer i+b.
- The routing sets To Computer j = From Computer j, so capture slot i carries source i+a+b.
- Euclid measures only a+b = 8 (mod 24).

**For an OUT-side slip (a = 8, b = 0):**
- On Talos, From Computer 17 = host slot 1, which gives a = +8.
- That was a different host (Intel controller, kernel 6.18.48), with ear's start order and Ethernet plugged in.
- One playback-side slip explains both sites.

**For an IN-side slip (a = 0, b = 8):** nothing beyond the fact that it also fits euclid's sum.

**When it happens:**
- The rotation is complete at the first non-zero IN sample (10:26:57.061807) and unchanged in every check through 10:27:13.
- Nothing happens on the host side at 10:26:57.06. The last host action that touched streaming was `SET_INTERFACE(1,1)` at 10:26:54.962215, followed by the first OUT URB at 10:26:54.967754.
- So the device latches the slip during its playback-path start: no earlier than interface 1's alt 1 and the first OUT packets, and no later than when its path opens about 2.1 s later.
- Once latched, it survives OUT microframe gaps: run 2 kept identity through the steps at 10:27:54.41 to 57.54.
- Only a device-side restart clears it. Run 2's device re-clocked from 192 kHz (interrupts until 10:27:47.454), opened its path 13 s after OUT began with both streams already steady, and came out aligned.

## 3. Ranked hypotheses, tested against the traces

1. **OUT starts late, is paced by IN, and gaps cause hopping.**

   - Refuted as the cause of the ~2 s loss. In run 1, IN carried full 432-byte packets with status 0 from IN URB 0 packet 4 (10:26:54.902749), and an OUT URB went out for every IN URB from 10:26:54.967754. The audio was zeros in content; there were no empty IN packets and no OUT stall.
   - The prediction of -18 statuses or start-frame jumps fails: there are no -18s, and start frames are unusable here.
   - Kept only in a narrower form, as T2: the start condition. The first OUT URBs go out with nothing queued (2 in run 1), and the steady queue is one URB.
2. **Capture first: `SET_INTERFACE(1,1)` while 0x87 is streaming.**
   - The prediction holds: in run 1, control #20 is the only request between IN start and the first OUT URB, and there is no rate SET.
   - Run 2 had the same order (alt 1 at 10:27:39.465, 72 ms into IN) and came out identity. But its device restarted its clock afterwards, so run 2 does not refute it.
   - `code.md` treats Talos as a refutation ("ear's order"), but that order was never recorded.
   - Kept, as T1.
3. **648-byte IN buffers.** Refuted. Run 1 has no -75 and no packet over 432 bytes; run 2 overflowed and came out identity.
4. **Rate or interface traffic.**
   - Refuted for run 1's 2.1 s loss: no rate SET, the clock read valid (01) at prepare (control #15 and #17), and there were no interrupts.
   - It does explain run 2's 13 s of silence.

5. **Malformed IN packets.** Refuted: every length is a multiple of 72.
6. **Fixed offsets, the 4-byte length header, channel maps, frame size, the packsize order bug, vendor interfaces.** Refuted: the OUT bytes on the wire are correct.
7. **The ~2 s loss is a separate device behaviour.**
   - The path opens with no host event, so it is device-internal.
   - The 2 starts without the loss still rotated by 8.
   - *Inference:* it belongs with mainline commit 320e557, where this model reports its clock invalid for over 2 s after a switch.

## 4. Mechanism: the two candidates and how to separate them

**Candidate A (preferred): an OUT-side slip.**
- The MOTU's OUT deframer counts the stream in 24-byte words. When its playback path starts under Linux's start pattern (T1 and/or T2), it ends up one word off: it drops one word, or starts its group counter at 1.
- From Computer j then gets host slot j+8 for the rest of the stream, and the IN side is correct.
- MOTU's own Mac driver avoids this start pattern:
  - It selects both alternate settings before any streaming (`mac-dext.md` D3.3-D3.4).
  - It starts OUT 320 ms after IN, on explicit frame numbers, with about 300 ms queued (D3.5, D3.8, D4.2, MI-D14).
- Apple's class driver (correct 3 of 3) also avoids it, though its order and queue depth are unknown.

**Candidate B: an IN-side slip.** The same one-word slip happens in the MOTU's IN framer, and OUT is clean. This needs Talos's playback shift to have had a different cause.

**Test to separate A from B.** Set the MOTU's routing to a single loopback route, From Computer 1 → To Computer 1, with every other route cleared. Then run the same `stock-quirk` step:

| Capture slot carrying a tone | Meaning |
|---|---|
| slot 1 carries source 9 | A: OUT slip |
| slot 17 carries source 1 | B: IN slip |
| slot 9 carries source 17 | both sides slipped by 16 |

If the front panel meters the outputs, there is a cheaper version: play a tone on host slot 1 only and see whether output 1 or output 17 lights. Output 17 means A.

**Test to separate T1 from T2**, a 2×2 with the current flags:

| | OUT paced by IN, shallow (T2 present) | OUT primed at start with `playback_first` (T2 absent) |
|---|---|---|
| capture first (T1 present) | today: +8 | test 2 |
| playback first (T1 absent) | test 1 | test 3 |

- **Playback first:** start `aplay` before `arecord`. Playback's prepare then sets interface 1 alt 1 and interface 2 alt 1 before any streaming, and the IN endpoint starts as playback's sync source (pcm.c:712-722, Ubuntu endpoint.c:1488-1521). That is the order MOTU's driver uses.
- **`playback_first`:** submits all 12 OUT URBs at start (Ubuntu endpoint.c:1603-1641). Each IN completion then releases one more (endpoint.c:468-537 and 1763-1836), so about 12 stay queued. The queue-depth count in `an1.py` should read about 12 instead of 1.

## 5. Fixes, in order of preference

### (a) Module parameters and quirk flags only

Each is one guarded `run-step`. After each, check the mapping, the queue depth (`an1.py`) and the time to first IN audio (`an5.py`). Repeat each at least 3 times, since results vary between starts.

1. `quirk_flags=07fd:0005:!validate_rates|skip_iface_setup|playback_first`, with `aplay` started before `arecord` (test 3). Removes both triggers and is closest to MOTU's own start. Strongest candidate.
2. The same string with `arecord` first, as today (test 2). Isolates T2. This matters for ear, which cannot always choose PipeWire's start order.
3. `quirk_flags=07fd:0005:!validate_rates|skip_iface_setup` (today's flags), with `aplay` first (test 1). Isolates T1 and needs no new flag.
4. If 1-3 all still rotate: `quirk_flags=07fd:0005:!validate_rates|skip_iface_setup|playback_first|iface_delay`. `iface_delay` waits 50 ms after every interface switch (Ubuntu endpoint.c:945-946), which tests whether the device needs time after alt 1 before OUT data arrives.
5. Diagnostic only, not a fix: `quirk_flags=07fd:0005:!validate_rates|skip_iface_setup|skip_implicit_fb`.
   - OUT becomes self-paced and deeply queued, which tests T2 without IN pacing.
   - **Risk:** with no feedback, OUT runs at the bus clock. The device runs about 1 frame every 4.94 s slower (the 360-byte packets), so its OUT buffer will eventually overflow and glitch.

Keep `!validate_rates|skip_iface_setup` in every string. Run 2 shows what happens without them: probe leaves the clock at 192 kHz, IN overflows 1623 times, and the watcher trips.

### (b) Small kernel patch (described, not written)

A start quirk for 07fd:0005 in `sound/usb/endpoint.c` and `pcm.c` that reproduces MOTU's own start:

- **Both alt settings first.** When either stream prepares, select alt 1 on both streaming interfaces before 0x87 starts. Never switch interface 1 while 0x87 is running.
- **Primed OUT.** Submit at least N ms of silent URBs on 0x09 at start and keep that queue depth, instead of one URB per IN completion. N = 2 ms is the RolandMueller1994 fork's `time_silent` floor; MOTU's driver queues about 300 ms. Keep the IN-matched packet sizes after priming.
- **Clock wait.** Backport the mainline 320e557 clock-valid wait for 0x0005. This covers probe and rate switches, not the shift.
- Optional: discard the first IN URB before starting OUT, as MOTU's driver does (D3.8, "skipping first in request").

### (c) Workarounds outside the driver

1. **Start playback before capture in ear.** Bring the card's playback outside node up before its capture node.
   - It costs nothing if test 1 or 3 fixes the shift.
   - **Risk:** PipeWire may suspend and restart nodes in another order (idle suspend, relinks), so every restart would need the same order.
2. **A fixed rotation in the application** (send `playback_N` to device slot N+8).
   - **Risk:** the shift is not guaranteed. Run 2 came out identity, and one earlier start looked N→N. A fixed offset would then put every channel on the wrong output with no warning.
   - Usable only with a check at every stream start. That check needs a known-good loopback channel, and a loopback measures only the sum of both slips.
   - Not recommended unless candidate A is confirmed and that check exists.
3. **Compensate in the MOTU's routing matrix** (From Computer N+8 → output N). Same risk as 2, but stored in the device, so it also applies to a start that came out correct. Not recommended.
4. **Restart the stream until it is aligned.**
   - Needs the same per-start check as 2.
   - Each start can cost about 2 s of the device's own mute.
   - Run 2 suggests that only a device restart clears a latched slip.
